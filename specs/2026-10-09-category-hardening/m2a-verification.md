**Date:** 2026-11-14. **Baseline:** CLI commit `682b443caa8a745910626f9e38f6ab706da874b2`.

**M2A is complete.** User confirmed independent Claude review finished with no remaining findings on **2026-11-14**. Implementation and local checks passed; hosted CI remains unverified. This record does not claim semantic-validator parity, Runner execution coverage, publication or deployment.

## Deliverables and boundaries

All changes are in `agentpm`:

- `standards/agentpm/1.0.0/conformance/fixture-index.json` contains **129 validation cases**: 32 conformant, 92 nonconformant, two unsupported and three incomplete. Evaluation levels: 89 standalone, 16 resolved-composition and 24 packaged-content cases.
- `fixture-index.schema.json` defines the test-data envelope and the comparator's result projection. This is not a universal APDS diagnostic API or an implementation's validation-result DTO.
- `fixtures/{valid,valid-cases,invalid,resolved,packaged}` contain real manifest and content inputs. The original nine structural positives are retained. Exact selected dependency edges distinguish different versions and owning dependency contexts without an AgentPM lockfile.
- `runner-observations.json` contains **28 separate observations**, including A–P capability/scope behavior and Q–T count/capacity/interval state sequences. These are supplied scenarios for an implementation's own runtime harness, not executions performed by the corpus checker.
- `compatibility/index.json` and `fixtures/compatibility/legacy-agent.json` keep historical missing-standard inference outside normative authoring validity. The expected compatibility state explicitly says `not_verified`, with no fabricated declaration or validation evidence.
- `conformance/run.py` is portable test infrastructure: bundle/index integrity, pinned-schema expectations, input references, rule mapping and comparison of independently supplied results. It contains no semantic validator, Registry client or Runner. Its output explicitly distinguishes corpus checks from evaluated implementation results and unexecuted observations.
- `conformance/README.md` provides prerequisites, repository-root and standalone-bundle instructions, single-case/full-suite/list commands, expected output/exit status, result projection and independent-implementation guidance. Supporting document links and `checksums.json` are synchronized.
- `scripts/check_apds_cli_fixtures.py` is deliberately **outside the APDS bundle**. It probes AgentPM lint and its known Knowledge reader. `scripts/test_apds_corpus.py` tests the corpus infrastructure and truthful comparison boundaries. `.github/workflows/ci.yml` runs the portable suite, checker tests and AgentPM acceptance probe; `.gitignore` excludes the documented local `.venv-apds` environment.

The vector positive uses one actual source/chunk and two little-endian float32 values. An actual `agentpm knowledge build` produced the index and derived manifest metadata without a provider/model call. Optional index build timestamps/version were omitted. `knowledge inspect --json` reports both manifest metadata and index fresh. The paired truncated binary fails on byte length. This sample representation is not a new universal APDS encoding requirement.

The quickstart test copies the **whole standalone bundle to a fresh temporary directory**, runs from outside the repository and uses the installed pinned dependency. It exercises the full corpus, one case, listing, unknown-case failure and one-result comparison. No Registry, credentials, Tools, models or Memory operations are used. Negative infrastructure tests reject changed/extra bundle files, duplicate case IDs, stale coverage, unsafe input paths, bad graph metadata or missing edge targets, missing/duplicate result IDs, wrong evaluation level/status, incorrect rule/document/path/severity, erroneous unevaluated checks, and falsely accepting an invalid fixture. Comparator unit tests construct expected projections solely to test comparison logic; they are **not** evidence that a semantic validator produced those results.

The full Rust workspace suite was not rerun locally: no Rust or product implementation changed. The targeted existing integration tests and actual acceptance probe are the relevant local checks; hosted CI retains its full workspace suite.

## Decisions, compatibility and remaining gates

- **D03:** Versioned JSON index with real files, selected graph edges and focused expected findings. A portable comparator accepts a test-only projection of native diagnostics. Independent implementations retain their own architecture and diagnostic serialization. Corpus checks, AgentPM implementation probes and Runner observations remain separate.
- **D19:** Explicit conformance states and evaluation levels; unavailable context is not authored invalidity, unsupported versions do not become conformant through fallback, and historical compatibility is not explicit standard declaration or verification. No Registry/lock/UI DTO is introduced in M2A.
- No production schema, API, database, SDK, authorization, private-package handling, publish/install behavior or shared Stage 1 contract changes. The manifest schema SHA-256 remains `f123150ff42cea4b29edb5076d7d70697269d20ad85118b4a07fe5af5cf2ab04`.
- **M2A review sign-off:** User confirmed Claude review complete with no other findings on **2026-11-14**. The review boundary includes fixture expectations, positive/negative pairs, role/scope mappings and quickstart usability. M2A is complete. Hosted CI is configured and remains unverified; this sign-off does not claim a hosted run.
- **Conformance-claim boundary retained after review:** Registry validators must identify their evaluated scope and unevaluated requirements. Passing generic corpus/schema checks does not establish semantic validation; passing validator cases does not establish Runner-dependent behavior. The user flagged this as an operational note for M2B/M2C, with no code change requested.
- **Later acceptance:** M2B/M2C implement and run independent validators on these exact inputs; M6A/M6B execute applicable Runner scenarios. These milestones must extend the quickstart with their actual integration commands without moving implementation-specific validators into the APDS bundle.
- No merge, tag or deployment was performed. The bundle is still an unpublished candidate; review any expectation change and resynchronize checksums before publication. Once published, do not rewrite its bytes or outcomes under the same standard version.

## Verification correction discovered during M2B

The [M2B verification record](m2b-verification.md#reviewed-corpus-and-probe-corrections) supersedes the earlier claim that the positive acceptance probe validated all 41 manifests. Existing lint discovery skipped non-`agent.json` filenames, and the old probe checked only process success. The corrected explicit-APDS probe requires actual validation reports and now evaluates all 41 positives. The inherited-only Skill fixture also had an unrelated MCP binding removed because it contradicted the intended positive case. No semantic rule, manifest schema or expected outcome was weakened; the unpublished candidate inventory was resynchronized. M2A's historical review sign-off is retained, and the corrections are covered by M2B's user-confirmed review sign-off and subsequent confirmation that all CLI hosted CI jobs passed; M2B is complete.
